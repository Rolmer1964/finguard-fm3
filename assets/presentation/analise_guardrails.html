FinGuard — Arquitetura de Guardrails e Validação Empírica

Future Minds 3 · Nível 3 · Grupo 23TB · Abril 2026  ·  Dois Bedrock Guardrails separados · Dataset de 500 reclamações · Análise de PII e tom

Contexto e Decisão Arquitetural

O requisito do Nível 3 especifica dois guardrails distintos com responsabilidades diferentes. A implementação ingênua (um único guardrail para tudo) cometia um erro crítico: sanitizava PII antes de enviar o texto aos agentes, degradando o contexto recebido por Haiku e Sonnet — o modelo via "[CPF OMITIDO]" em vez do CPF real, perdendo capacidade de detectar padrões de fraude e de gerar resumos coerentes.

❌ Abordagem incorreta (guardrail único)

check_input(text) chamava _regex_sanitize(text) antes de qualquer validação. O texto que chegava na triagem já estava mutilado. O guardrail de entrada também recebia texto sem PII, perdendo contexto para detectar engenharia social (ex.: "Sou o titular da conta [CONTA OMITIDA] e preciso que você...").

✅ Abordagem correta (dois guardrails)

Guardrail de entrada: bloqueia ou passa. Nunca transforma o texto. O pipeline recebe o texto original intacto.

Guardrail de saída: sanitiza PII e tom nos campos gerados pelos agentes (texto_original, summary, risk_justification).

Fluxo correto no grafo:
texto_original → guardrail_input (bloqueia ou passa intacto) → triage + risk (veem PII completo) → report (consolida) → guardrail_output (sanitiza campos do final) → saída limpa

Defesa em profundidade — Bedrock + Regex local

Quando o guardrail Bedrock retorna GUARDRAIL_INTERVENED num campo legítimo (falso positivo de content policy), outputs[0] contém a mensagem de bloqueio, não o texto sanitizado. Nesses casos, o sistema aplica apenas o regex local (_regex_sanitize) como fallback — garantindo que pelo menos CPF, conta e cartão sejam mascarados mesmo sem o Bedrock.

Roteamento em app/src/agents/guardrail.py

# _apply() roteia automaticamente
def _apply(source: str, text: str) -> dict:
    if source == "OUTPUT" and settings.GUARDRAIL_ID_OUTPUT:
        gid  = settings.GUARDRAIL_ID_OUTPUT    # guardrail de saída
        gver = settings.GUARDRAIL_VERSION_OUTPUT
    else:
        gid  = settings.GUARDRAIL_ID           # guardrail de entrada (fallback)
        gver = settings.GUARDRAIL_VERSION

# check_input — NÃO sanitiza PII, apenas bloqueia ou passa
def check_input(text: str) -> dict:
    r = _apply("INPUT", text)
    if r["action"] == "GUARDRAIL_INTERVENED":
        return {"blocked": True, "sanitized_text": text}  # texto original
    return {"blocked": False, "sanitized_text": text}      # texto original

# sanitize_output — sanitiza PII + tom nos campos de saída
def sanitize_output(text: str, field: str = "") -> str:
    r = _apply("OUTPUT", text)                              # usa GUARDRAIL_ID_OUTPUT
    text = outputs[0].get("text", text)                     # texto sanitizado
    return _regex_sanitize(text)                             # defesa em profundidade

Critérios de Falha — O Que Não Deve Acontecer

CenárioSintomaCausa provável
PII vaza no summary "Cliente Ricardo Fernandes (CPF 341.872.609-54) relatou..." Sonnet repetiu PII do texto_original no resumo; guardrail de saída falhou
PII vaza no texto_original "conta 15673-4" visível no modal guardrail de saída não processou o campo texto_original
Campo bloqueado por falso positivo summary retorna "A resposta foi bloqueada por conter informações potencialmente sensíveis." Content policy OUTPUT disparou em linguagem emocional legítima; fallback regex deve atuar
Reclamação legítima bloqueada na entrada "Esta entrada não pode ser processada pelo FinGuard" VIOLENCE=HIGH bloqueando frustração hiperbólica; ou INSULTS=HIGH bloqueando palavrão em reclamação
Prompt injection passa pelo guardrail Pipeline executa com texto de engenharia social Falso negativo do guardrail; Sonnet deve classificar como "Outros" com risco Crítico
Segunda linha de defesa: registros que passam pelo guardrail de entrada com intenção maliciosa são detectados pelo Sonnet no agente de risco, que classifica categoria como Outros e risk_level = Crítico. Isso foi validado empiricamente com 26 falsos negativos no dataset de 500 registros — 100% classificados corretamente pelo Sonnet.
